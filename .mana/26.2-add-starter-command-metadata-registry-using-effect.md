Goal: add the next substrate layer after `src/effects.rs`: a small command metadata registry for a starter set of AUSH builtins. This should make commands inspectable internally without changing execution behavior yet.

Current state:
- `src/effects.rs` defines `CommandEffect`, `RiskLevel`, `EffectPresentation`, and `render_effect_summary()`.
- `src/lib.rs` exports `pub mod effects;`.
- Unit 26.1 established the UX rule: raw effect IDs are for JSON/schema/debug; terminal UI uses polished labels.

Steps:
1. Add a module such as `src/command_metadata.rs` defining:
   - `CommandMetadata` or `CommandSpec` with fields like `name`, `summary`, `effects: &'static [CommandEffect]`, `risk: RiskLevel`, `supports_json`, `supports_preview`.
   - helper methods for machine JSON-ish data later and pretty human summaries now.
2. Seed metadata for a small starter set only:
   - safe/read: `ls`, `cat`, `grep`, `find`, `git_status`
   - mutating/local: `rm`, `mv`, `cp`, `write_file`
   - network: `fetch`
   - process: maybe external command fallback as `spawn_process` if represented cleanly; skip if it complicates scope.
3. Add lookup helpers:
   - `metadata_for_command(name: &str) -> Option<&'static CommandMetadata>`
   - `all_command_metadata() -> &'static [CommandMetadata]`
4. Add tests proving:
   - `rm` has `DeleteFile` and high risk.
   - `fetch` has `NetworkAccess`.
   - `ls`/`cat` labels render prettily through effects.
   - unknown commands return `None`.
5. Export the module from `src/lib.rs` if needed.

Files:
- `src/command_metadata.rs` (add)
- `src/lib.rs` (modify — export module)
- inline tests in the module preferred.

In scope:
- metadata registry and tests only.
- no behavior changes.
- no CLI flags yet.

Out of scope:
- `--schema` CLI.
- approval gates.
- receipts ledger.
- integrating with builtin dispatch.
- broad command catalog.

Do not:
- print raw effect IDs in human summaries.
- refactor builtins.
- touch unrelated dirty files.
