Goal: add receipts ledger v0 as substrate only: a serializable command receipt model, pretty human rendering, and JSONL append helper. Do not wire it into command execution yet.

Current state:
- `src/effects.rs` defines stable machine effect IDs and polished human labels.
- `src/command_metadata.rs` maps starter commands to effects/risk and can render human summaries.
- UX constraint: terminal-facing receipt output must be polished (`Delete files`, `High risk`) and should not expose raw IDs like `delete_file` unless JSON/debug output is explicitly requested.

Steps:
1. Add `src/receipts.rs` defining a v0 receipt model with fields such as:
   - command string
   - cwd
   - started_at / finished_at
   - duration_ms
   - exit_code
   - declared effects (`Vec<CommandEffect>`)
   - risk (`RiskLevel`)
2. Add constructors/helpers that can build a receipt from optional `CommandMetadata`; known commands inherit metadata effects/risk, unknown commands should remain conservative but not overcomplicate behavior.
3. Add JSONL append helper, e.g. `append_receipt_jsonl(path, &receipt)`, creating parent dirs if needed.
4. Add pretty terminal renderer, e.g. `render_human_receipt(&receipt)`, using effect labels and risk labels, not raw IDs.
5. Add focused tests proving:
   - JSON serialization uses machine IDs (`delete_file`).
   - pretty rendering uses `Delete files` and does not include `delete_file`.
   - appending writes one JSONL receipt that can be deserialized.
   - metadata for `rm` produces high-risk delete-file receipt.
6. Export the module from `src/lib.rs`.

Files:
- `src/receipts.rs` (add)
- `src/lib.rs` (modify)

In scope:
- data model, JSONL helper, pretty renderer, tests.

Out of scope:
- automatic recording from executor.
- default receipt path policy.
- semantic history UI.
- approval gates.
- background/durable job receipts.

Do not:
- change shell runtime behavior.
- print raw effect IDs in human receipt rendering.
- add new dependencies.
